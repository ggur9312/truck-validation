# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A browser bookmarklet (Korean UI) that automates a warehouse WMS's "집품 현황 조회" (pick-status lookup) page: scan a tote barcode → auto-search → detect truck vs. courier delivery → verify scanned products against expected quantities → for courier shipments, auto-open the WMS's waybill-generation modal and drive it via a scannable virtual barcode. There is no access to the real WMS; all development is verified against a hand-rolled mock (`test/fixture.html` + `test/server.js`).

`package.json`'s `test:smoke` script only wires up `smoke.js` + `smoke_truck.js` — the other smoke files above are not in any npm script and must be run individually. There is no test runner/framework; each file is a plain Node script that `console.log`s `OK:`/`FAIL:` lines and sets `process.exitCode`. Every smoke test starts its own instance of `test/server.js` (a plain `http` server on port 8934) as a side effect of `require`, so run smoke tests as separate `node` processes (as above), not concurrently in the same process.

After any change to `src/bookmarklet.js`, run **all** of the commands above (unit test + all 16 smoke files) before considering the change done, then `node build.js` and sanity-check `dist/bookmarklet.txt` (e.g. `node -e "new Function(require('fs').readFileSync('dist/bookmarklet.txt','utf8').replace(/^javascript:/,''))"`) — `dist/bookmarklet.txt` is the actual shipped artifact and is committed to git (not gitignored), so it must be rebuilt and committed alongside any `src/` change.

## Architecture

**Everything lives in one file, `src/bookmarklet.js`.** It is a single IIFE prefixed with the `javascript:` scheme (a labeled statement, not a syntax error) and has zero runtime dependencies — no CDN, no bundler, no framework. This is a hard constraint, not an oversight: the target network's CSP blocks external scripts, so the CODE128B barcode encoder + `<canvas>` renderer is hand-written inline (`code128Values`/`code128Patterns`/`drawCode128`) rather than pulled from a library.

Top-of-file constants are the seams for adapting to a real WMS whose DOM differs from the mock:
- `SEL` — every DOM selector the script touches on the *host* WMS page (tote input, search button, date-range picker, waybill dialog, etc.)
- `CTRL` — the short strings (`TVCS`/`TVCW`/`TVCR`) encoded into the virtual barcodes; kept intentionally short (4 chars) because the CODE128 module count — and therefore the on-screen widget width — scales directly with string length (this was cut down from `TVCTL_WAYBILL`-style 13-char codes in a prior round specifically to shrink the floating barcode without thinning the bars past scannable width)

**Virtual barcode mechanism**: barcode scanners are keyboard-emulation devices. A CODE128 barcode is rendered on a `<canvas>`; scanning it types the encoded string into whatever's focused, followed by Enter. The global `keydown` listener (`onGlobalKeydown`) buffers keystrokes and uses inter-key timing to distinguish scanner input (fast) from human typing (slow), then checks whether the buffered string starts with `TVC` to route it to `handleScan` as a control code vs. letting it fall through as a real product/tote/box barcode typed into the WMS's own input.

**State machine**: `state.mode` drives everything (`IDLE` → `SEARCHING` → `VERIFYING` → `WAITING_WAYBILL_OPEN` → `WAITING_WAYBILL` → `REFRESHING` → `REPRINT_READY` → back to `IDLE`). Most functions are guarded by a mode check so stray scans in the wrong state are no-ops.

**UI isolation**: a single host `<div>` is appended to `document.documentElement` with `attachShadow({mode:'open'})`; the entire stylesheet is one big JS string (`CSS`) injected as a `<style>` tag inside the shadow root, using CSS custom properties (`--tv-*` tokens on `:host`) for the whole dark theme. Nothing is written to global document styles.

**Waybill modal detection, worth knowing before touching the waybill-watching logic:** the real WMS's waybill modal is a persistent `<div id="modalOutboundWaybill">` — it is never added to or removed from the DOM by opening/closing; instead its `class` toggles between `waybill-overlay is-open` (open) and `waybill-overlay` (closed). `findWaybillModalNode()` therefore treats presence of the `is-open` class on `SEL.waybillDialog` (`#modalOutboundWaybill`) as the *authoritative* open/closed signal when that element is found at all — it does **not** fall back to geometry checks for it, since a hidden-but-still-rendered descendant (e.g. via `visibility`/`opacity` instead of `display:none`) could report nonzero `offsetWidth`/`offsetHeight` forever and mask a real close. Geometry-based visibility (`isElementVisible`, via `offsetWidth`/`offsetHeight`/`getClientRects().length`) is used only for the two fallback candidates (`SEL.waybillSubmit`/`SEL.waybillBoxInput`), which is what kicks in when `SEL.waybillDialog` doesn't match at all (real WMS markup drifted from our assumed id — see `smoke_fallback.js`). Because the modal is a persistent element with a toggled class rather than a node that gets inserted/removed, `watchWaybillDialog()`'s `MutationObserver` watches `attributes`/`class` (not just `childList`) so a manual close is caught immediately instead of waiting for the 400ms poll fallback.

**Group-number loading restriction (상차제한)**: settings has a `restrictedGroups` field (comma-separated raw string, edited via the `.tv-group-input` text field in the settings modal, parsed on demand by `getRestrictedGroupList()`) and a `restrictionEnabled` boolean (the `SETTING_DEFS`-driven "그룹번호 상차제한" toggle switch). The actual restriction decision in `processRow()` is `state.settings.restrictionEnabled && getRestrictedGroupList().indexOf(restriction.groupNo) !== -1`; both the switch and the group list must agree for a tote to be treated as restricted. The `.tv-group-field-row` text input is only rendered visible when `restrictionEnabled` is true, and is rendered *directly below its own toggle row* (not grouped with other fields at the bottom) — `renderSettingsHTML()` sets its initial `tv-hidden` state from that flag, and the toggle's `change` handler in `bindSettingsEvents()` additionally toggles it live by checking `cb.dataset.key === 'restrictionEnabled'` directly (not generalized across `SETTING_DEFS`, since each toggle currently gates a differently-shaped field below it). The group number, creation date, and vendor name shown when restricted all come from the *same* detail document already being fetched for truck/courier detection (`linkType`, the 3rd `<td>`'s link) — `parseRestrictionInfo(doc)` reads the group number from that doc's 1st table/1st `<td>`, the creation date from the 1st table/6th `<td>` (sliced to the first 10 chars to normalize to `YYYY-MM-DD` in case the real WMS includes a time component), and the restricted-vendor name from its 2nd table/1st `<td>`, which is a different field from `info.vendor` (fetched from the *other* detail link, `linkProduct`/1st `<td>`, 1st table/5th `<td>`) even though both are commonly the same company in practice. When the tote's group number matches, `state.toteInfo.isRestricted` is set and `openVerifyModal()` renders the type banner in an orange `restricted` variant (`🚫 상차제한 · <vendor>`) instead of the normal truck/courier one — and `afterVerification()` checks `isRestricted` before `isTruck`, so a restricted tote always ends after verification (no waybill modal), the same as the truck flow, even if it's actually a courier delivery.

**Creation-date loading restriction** works the same way as group-number restriction but as an independent, OR'd condition (`isRestricted = groupRestricted || dateRestricted` in `processRow()`) — either one alone is enough to restrict a tote. `state.settings.dateRestrictionEnabled`/`dateRestrictionStart`/`dateRestrictionEnd` (the `.tv-date-start-input`/`.tv-date-end-input` native `<input type="date">` fields, which get the browser's own calendar picker for free) drive `isDateInRestrictedRange()`. **The range is open-ended on either side**: only a start date restricts that date and everything after it (`dateStr >= start`); only an end date restricts that date and everything before it (`dateStr <= end`); both together form the usual inclusive closed range — all via plain string comparison, which works correctly for zero-padded ISO dates without any `Date` object / timezone handling. The status-badge date line mirrors this: a closed range reads `생성일시 : start ~ end` (spaced), but an open-ended range reads `생성일시 : start~` or `생성일시 : ~end` (no spaces around the lone `~`) — see the ternary in `updateRestrictBadge()`.

**Every setting resets on every load, none persist** — `restrictionEnabled`/`restrictedGroups` used to be the exception (persisted, `restrictionEnabled` defaulted `true`) but that was changed on request: now `SETTINGS_RESET_ON_LOAD` lists every key in `SETTINGS_DEFAULTS` (both toggles off, all three text/date fields empty), so a fresh load or reload always starts from a fully blank slate — the localStorage read/write plumbing (`loadSettings()`/`saveSettings()`) is kept as-is for architectural consistency (and in case a future non-restriction setting needs to persist), it just currently has no persisting effect since every key is in the reset list. **Pitfall already hit once**: `SETTINGS_DEFAULTS`/`SETTINGS_RESET_ON_LOAD` must be declared *before* `var state = { settings: loadSettings(), ... }`, not after — `var` hoisting only hoists the name binding, not the assignment, so if `loadSettings()` runs before those two vars are assigned, they're `undefined` at that point, `SETTINGS_RESET_ON_LOAD.forEach` throws, and the `try/catch` in `loadSettings()` silently swallows it into an empty settings object (every toggle defaults unchecked, every field hidden) — no visible error, just wrong defaults.

**Search-result row must be validated before verification starts**: `startSearch()` compares the resolved row's 1st `<td>` (the same text the WMS itself shows as the tote identifier) against the barcode that was actually scanned, via `td(row, 0) !== toteBarcode` — a mismatch (stale/wrong result) is rejected with a toast instead of silently verifying the wrong tote. `processRow()` then separately requires the last `<td>` to contain either the reprint button (`.btn-waybill-print-single`) or the waybill-generation button (`[data-action="open-waybill-modal"]`); a row with *neither* is a tote that cannot be loaded at all and is rejected with "상차 불가한 토트입니다" before ever fetching detail pages or opening the verify modal. See `smoke_row_validation.js` (fixture scenarios `TOTE_MISMATCH` and `TOTE_NOBTN`).

`.tv-status-overlay` (all `showStatus()` toasts) is anchored `align-items:flex-start` with `padding-top:90px`, not vertically centered — this is deliberate so a toast never visually collides with the verify/settings modals it often appears alongside.

**Product mismatch during verification uses a blocking modal, not a toast**: `markProductScan()`'s two mismatch branches (unknown barcode, already-fully-scanned barcode) call `showMismatchModal(message, scannedBarcode)` instead of `showStatus(...)` — unlike a toast, `.tv-mismatch-overlay` never auto-hides; it stays up until the user clicks `.tv-mismatch-close` or presses Enter. `.tv-mismatch-overlay`'s `background` is `transparent` (no dimmed/blurred backdrop like the other `.tv-overlay`s use, e.g. `.tv-overlay.tv-corner`'s same pattern) — only the floating `.tv-mismatch-card` itself is visible, the WMS page behind it is not dimmed; the overlay element still covers the full viewport (`position:fixed;inset:0`) purely to center the card and intercept clicks/keys until dismissed, it just isn't painted. The actual barcode that was scanned is echoed back (`.tv-mismatch-scanned`) so the user can tell at a glance whether it was a genuine wrong item or a misread. `onGlobalKeydown()` checks `ui.mismatchOverlay.classList.contains('tv-show')` as its very first branch and, while open, intercepts Enter specifically to close the modal (`preventDefault`/`stopPropagation`/`resetScanBuf()`) instead of letting it fall through to the scan-buffer or fast-path search logic — any other keys are ignored outright (return early) so a scan attempted while the modal is blocking doesn't get processed as a new product scan; the user must dismiss first, then rescan. **`.tv-mismatch-card` deliberately does *not* use the shared `.tv-card` class** (it duplicates the handful of properties it needs instead) — nearly every smoke test's very first assertion is `page.locator('.tv-card').waitFor(...)` to find the initial settings card, and adding a second permanently-in-DOM `.tv-card`-classed element (even one that starts hidden) turns that into a strict-mode "resolved to 2 elements" failure across the entire suite, since Playwright's strict mode counts DOM matches regardless of visibility.

**The "검증 중 (X/Y)" hero counter tracks scanned *units*, not scanned *product types***: `updateHero()` sums `p.required`/`p.scanned` across every entry in `state.expected` rather than counting how many products are individually "done" — so a tote needing BAR001×2 + BAR002×1 shows "1/3" after a single BAR001 scan, not "0/2". This intentionally does *not* use `state.toteInfo.totalQty` (the separately-fetched "전체 집품수량" figure, shown as a small caption on the 토트바코드 stat tile — see below) as the denominator, since that field isn't guaranteed to equal the sum of the individual products' required quantities (the fixture data doesn't, on purpose, to catch exactly this mistake) — using it would risk a counter that never reaches "done" even once every product is actually fully scanned. Since `markProductScan()` already refuses to over-scan a product (`p.scanned >= p.required` is the mismatch branch), `scannedQty === totalQty` is always exactly equivalent to "every product individually done," so this also doubles as the completion check with no behavior change to when `completeVerification()` fires.

**Verify modal redesign — delivery-type tile, quantity placement, hero-as-a-line, bigger icons, lighter font weight**: `.tv-type-banner` used to be a full-width colored strip sitting above `.tv-stat-grid`; it's now the grid's *third cell*, sized like the other two `.tv-stat-tile`s (업체명/토트바코드) so the delivery method (택배=green/트럭=red/상차제한=orange) reads as one of three equal stat cards rather than a separate banner. The gradient background (and the `tvTypeGlow` pulse animation) still lives directly on `.tv-type-banner` itself, not on a nested child — `smoke_group_restriction.js` asserts `getComputedStyle(.tv-type-banner).backgroundImage` contains the orange gradient's literal `rgb(251, 146, 60)`, so the color must stay on that element. `tvTypeGlow`'s inset-glow numbers were scaled down (`50px 8px` → `22px 5px`) to suit the smaller tile instead of the old full-width strip. `.tv-type-banner-value` uses `flex-wrap:wrap` + `word-break:keep-all` so the longer restricted-tote text (icon + "상차제한 · <vendor>") wraps onto a second line inside the narrow tile instead of overflowing it. **`tvTypeGlow` remains the only looping animation in the modal** — the stat tiles, header, and hero are all static, so the delivery-method indicator is the sole animated element, as intended. `info.totalQty` ("전체 집품수량") is rendered as a small `.tv-stat-caption` under the 토트바코드 tile's value (e.g. "전체 7개"), not in the hero — see next.

`.tv-verify-hero` used to be a bulky icon-circle + two-line text block (~70px tall); it's now a single compact row — a thin `.tv-hero-track`/`.tv-hero-fill` progress bar (width set to the scanned/total percentage in `updateHero()`) plus the `.tv-hero-title` counter text beside it, both on one line (~39px tall), because the old block wasted vertical space the product list could otherwise use. `.tv-hero-title`'s text format (`검증 중 (X/Y)`) is unchanged since `smoke.js` asserts its exact string; only the surrounding markup (`.tv-hero-icon`/`.tv-hero-text`/`.tv-hero-sub` and the `tvHeroPop` keyframe) was removed. Icons inside the verify modal were enlarged for legibility: `.tv-verify-header-icon` 34px→42px, `.tv-stat-icon` 32px→40px, `.tv-type-banner-icon` 16px→20px, `.tv-product-status` 26px→30px.

**Every `font-weight:800` in the whole stylesheet (not just the verify modal) was brought down to `700`**, and most `font-size` values got a uniform ~1.5px bump for legibility, project-wide (settings modal, status toast, mismatch modal, status badge, verify modal, product rows, floating barcode labels) — Malgun Gothic only ships a Regular(400)/Bold(700) face, so requesting `800` forces the browser to synthesize an extra-bold weight beyond the real bold face, which read as smudged/muddy on complex Korean glyphs; capping at the font's actual bold weight avoids that synthesis entirely. `smoke_group_restriction.js`'s font-size assertion between `.tv-status-badge-main` and `.tv-status-badge-restrict-header` only checks the two are *equal to each other*, not any hardcoded pixel value, so both were bumped together and the test stays valid regardless of the absolute size chosen.

The top-right status badge (`.tv-status-badge`) is a single box: `.tv-status-badge-main` (always shown once activated, "🟢 트럭검증 활성화"), then a single shared `.tv-status-badge-restrict-header` ("🚫 상차제한 활성화 중", same 18px font-size as `.tv-status-badge-main` by request) shown whenever *either* restriction type is active, followed by up to two independent `.tv-restrict-detail-line` rows — `.tv-restrict-group-line` ("그룹번호 : …") and `.tv-restrict-date-line` ("생성일시 : …") — each shown only when its own restriction is configured, so both can appear together under the one shared header. All three are driven by a single consolidated `updateRestrictBadge()` (there used to be two separate per-type functions/badges with their own "X 상차제한 활성화" headers each; merged into one shared header + itemized detail lines on request), called from `showActiveIndicators()`, the group/date input handlers, and the generic `SETTING_DEFS` checkbox handler in `bindSettingsEvents()`. The detail lines are set via `textContent` (not `innerHTML`), so no manual escaping is needed despite echoing user-entered text. The badge's width is `max-content` (not a fixed px value) so it always hugs its content regardless of how many lines are showing.

**The waybill-generation virtual barcode lives inside the status badge, not a separate floating overlay**: `.tv-status-badge-waybill` is the last child of `.tv-status-badge` (after the restriction detail lines), shown/hidden via plain `tv-hidden` class toggling on `ui.waybillSection` (set once at `initUI()` time to `shadow.querySelector('.tv-status-badge-waybill')`) rather than the Popover-based mechanism the reprint overlay still uses. `showWaybillOverlay()` sets its `innerHTML` (label + canvas wrapper) and draws the CODE128 barcode into it; `hideWaybillOverlay()` re-hides it and clears the markup so a stale barcode/canvas never lingers. This replaced an earlier separate `.tv-waybill-area` popover pinned to the top-right of the viewport — moving it into the always-visible badge means the waybill barcode is anchored in one predictable place instead of floating independently over WMS content.

**Settings window is a toggle, not an always-open action panel**: the gear button (bottom-left) calls `toggleSettings()`, which closes the settings card if it's already open instead of just re-rendering it — this matters because the card can also be opened centered (first run, `openSettingsModal(true)`) or as a small corner popup near the gear (`openSettingsModal(false)`, used once already activated), and a naive "always open" handler would make the corner popup impossible to dismiss via the gear itself. The action button's label reflects `state.settings.enabled` at render time — `활성화` before the very first activation, `저장` on every subsequent open (e.g. reopened via the gear to edit `restrictedGroups`) — the click handler itself is unchanged either way (unconditionally sets `enabled = true`, saves, closes, shows the active indicators), so whatever toggles/fields are currently configured in the form are what get applied.

The floating reprint virtual-barcode overlay (`.tv-reprint-area`) uses the CSS Popover API (`popover="manual"` + `showPopover()`/`hidePopover()`, see `setPopoverVisible`) to render above the WMS's own high-z-index overlay, with a `classList.toggle('tv-show', …)` fallback for browsers without Popover support. (The waybill barcode used to share this mechanism via a `.tv-waybill-area` popover but no longer does — see above.)

**`afterWaybillClosed()` must not assume the waybill was actually generated**: the WMS's waybill modal can be dismissed by the user without completing generation (its own close button, clicking outside, etc.) — the `MutationObserver` in `watchWaybillDialog()` only detects that the modal *closed*, not why. After the modal closes and the page re-searches the tote, `afterWaybillClosed()` calls `rowHasReprintButton(row)` (a small helper factored out of the identical check already in `processRow()`, checking whether the resolved row's last `<td>` contains `.btn-waybill-print-single`) before showing the reprint barcode — only a row that now actually has the reprint button gets `showReprintOverlay()`; otherwise `state.mode` goes back to `IDLE` with an error status ("운송장이 생성되지 않았습니다"). Previously `waitForSearchResult(prevRowEl).then(showReprintOverlay, showReprintOverlay)` called `showReprintOverlay` unconditionally on both the success *and* failure branches, so manually closing the modal without generating a waybill still surfaced a reprint barcode that would do nothing useful if scanned. See `smoke_manual_close.js`.

**Watch out for the `overflow-x`/`overflow-y` coupling gotcha**: per the CSS Overflow spec, setting only one of `overflow-x`/`overflow-y` to a non-`visible` value computes the *other* axis to `auto` too (never `visible`) if left unset. `.tv-product-list` only needs vertical scrolling (`overflow-y:auto`), but leaving `overflow-x` unset made it implicitly `auto` as well — and a product row's error-shake animation (`tvRowFocusErr`, `translateX` up to 6px) transiently pushed `scrollWidth` past `clientWidth`, flashing a real horizontal scrollbar on every mismatched/duplicate scan. Any scrollable container that should only scroll on one axis needs the other axis pinned to `hidden` explicitly, not left to default.

**Row scan-feedback glow must use `inset` box-shadow, not an outward one**: `.tv-product-row` sits flush against `.tv-product-list`'s edges with zero horizontal gutter, and that list has `overflow-x:hidden` (see the coupling gotcha above). An *outward* `box-shadow` ring (`tvRowFocus`/`tvRowFocusErr`, the blue "scanned correctly" / red "mismatch" glow) bleeds past the row's own left/right edges to render the ring — but those edges coincide exactly with the list's own clip boundary, so the left/right (and most of each rounded corner's outward curve) got silently clipped away, leaving only the top/bottom edge strips and the slivers of each corner nearest the clip boundary visible — which reads as "only the corners flash" instead of the whole row lighting up. Both keyframes now paint the ring with `inset` (`box-shadow:inset 0 0 0 5px rgba(...)`), which stays entirely within the row's own border box and can never be clipped by an ancestor's `overflow`, regardless of how tight the surrounding gutter is. The `tvRowFocusErr` shake's `translateX` transform is unrelated to this and is untouched — it still visibly clips at its most extreme frames, which is the accepted tradeoff that keeps the scrollbar from flashing (see above).

**Verify modal height capping**: `.tv-verify` has `max-height:88vh` and is itself a column flex container (header + body), so with enough products the *card* can never grow past the viewport the way it used to. Inside `.tv-verify-body` (also a column flex container), every section except `.tv-product-list` is `flex-shrink:0` (hero, type banner, stat grid, tip bar, skip-area) so they always render at full size; `.tv-product-list` is the sole `flex:1` element and absorbs whatever space is left, scrolling internally past its `min-height` floor. `.tv-verify-body` also carries its own `overflow-y:auto` (with `overflow-x:hidden`, per the coupling gotcha above) purely as a fallback for pathologically short viewports where even the `flex-shrink:0` chrome can't fit in 88vh — normally a no-op since content fits, but it guarantees `skip-area` is always at least reachable by scrolling rather than silently clipped by `.tv-verify`'s own `overflow:hidden`. See `smoke_many_products.js`.

**Reprint barcode stays available for repeat use**: `doReprint()` deliberately does *not* hide `.tv-reprint-area` or move `state.mode` out of `REPRINT_READY` after a successful reprint — some totes genuinely need reprinting more than once (lost/damaged label), so the barcode must stay scannable indefinitely. The only way out of `REPRINT_READY` is scanning a new tote barcode (handled by `handleScan`'s `REPRINT_READY` branch, which hides the stale overlay and starts a fresh search).

**Watch out for the `CSS` name collision**: the file's own top-level stylesheet variable is `var CSS = '...'`, which shadows the global `window.CSS` namespace object *everywhere in this file's scope*. Calling `CSS.escape(...)` will silently resolve to a property on the stylesheet string, not the browser API, and throw `CSS.escape is not a function` at runtime — this bit us once already. Find elements by attribute value via a manual `Array.prototype.filter` over `.children` (see `findProductRow`) instead.

**Row/element animations use a specific pattern to avoid killing each other**: several CSS keyframe animations are triggered by adding a class, and re-triggered later by `classList.remove(cls); void el.offsetWidth; classList.add(cls)` (forces a reflow so the animation restarts). Entrance animations (`.tv-row-enter`) are intentionally *not* combined with `animation-fill-mode: forwards` on the same element that later gets a different animation class (`.tv-row-pop`/`.tv-row-focus`) — two different animation-name values on overlapping classes fully override each other (CSS `animation` is not additive across selectors), so relying on `forwards` to hold a value (e.g. opacity) breaks the moment a second animation class gets added later. Give each transient animation its own modifier class with a self-contained resting state instead of depending on fill-mode carryover from an earlier one.

**Testing strategy**: there is no access to the real WMS, so `test/fixture.html` + `test/server.js` (plain Node `http` server, no deps) is a hand-rolled stand-in matching just the DOM shape the script depends on (`SEL`/`CTRL` contract). Playwright smoke tests load `src/bookmarklet.js` directly from disk (`fs.readFileSync` + strip the `javascript:` prefix + `page.evaluate`), not the built `dist/bookmarklet.txt` — so tests exercise source, and rebuilding dist is a separate manual verification step, not something the test suite covers.

`dist/screenshots/*.png` (written by `test/screenshot.js`) is not gitignored but is treated as a scratch/review artifact in this workflow — generated to inspect visually or send to the user, then deleted (`rm -rf dist/screenshots`) rather than committed.
